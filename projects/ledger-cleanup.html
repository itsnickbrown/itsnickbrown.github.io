Data quality

Finding and fixing bad POS data

The ledger said one month was up 93%. It wasn't. How I traced double counting, name splits and end users hiding in the reseller list, and fixed them without deleting real revenue.

What went wrong

Distributor files are cumulative: each one repeats the month so far. The ledger was supposed to skip lines it already had. It didn't, because the line ID hashed raw Excel values, and the types drifted between exports. Line 3 in one file was 3.0 in the next. Same sale, new ID, counted again. One month read 93% high.

The fix

I normalized every field before building the ID, then wrote a one-time cleanup. The key detail is what it leaves alone. Older rows from the corporate report have no line numbers and only half have invoice numbers. Two real units of the same part to the same customer in the same month look exactly like a duplicate. Deduping those would delete real revenue, so the script skips them.

Name splits and fake partners

The same company showed up under a DBA, an FKA, an account number suffix or a "(GOVT ONLY)" tag. One record looked like it was buying and the other looked like it had stopped. I kept a merge map in the code, checked each pair by raw name, and added about 90 entries. Acquisitions went in too, so a buyer that now orders under its new owner's name stays one partner.

Then there were 79 "partners" that were actually end users, because one distributor puts the customer in the reseller field. They came out of enrichment and mailing lists. A month of data was missing entirely, which quietly drags down every trailing-12 number, so the dashboard now prints a warning band whenever a month has no rows.

What the cleanup turned up

  • The tier workbook covered 199 of about 1,625 partners. Roughly 320 buying partners were in no tier.
  • The newsletter list reached 30 of 450 buying partners and had a 23% hard bounce rate. I rebuilt it from the ledger.
